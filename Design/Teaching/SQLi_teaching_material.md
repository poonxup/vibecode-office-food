## วัตถุประสงค์การเรียนรู้

เมื่อจบบทเรียนนี้ นักศึกษาจะสามารถ

1. อธิบายได้ว่า SQL Injection คืออะไร และเกิดจากหลักการใด
2. ชี้จุดที่ “ต่อสตริง SQL กับค่าจากผู้ใช้” ในโค้ดได้
3. อธิบายได้ว่าอินพุตหนึ่ง ๆ ทำให้คำสั่ง SQL เปลี่ยนความหมายอย่างไร
4. เขียนฝั่งเซิร์ฟเวอร์ให้ปลอดภัยด้วย parameterized query / prepared statement และอธิบายมาตรการเสริม (validation, least privilege, ไม่เปิด raw SQL ให้ผู้ใช้)

## 1. SQL Injection คืออะไร เกิดได้อย่างไร

**SQL Injection** คือช่องโหว่ที่เกิดเมื่อโปรแกรมนำค่าจากผู้ใช้ (เช่น ช่องค้นหา, query string, ฟอร์ม) ไป **ประกอบเป็นข้อความคำสั่ง SQL โดยตรง**

ฐานข้อมูลไม่ได้แยก “โค้ด SQL” กับ “ข้อมูล” เองถ้าโปรแกรมส่งมาเป็นสตริงก้อนเดียว ดังนั้นถ้าผู้ใช้พิมพ์เครื่องหมายอัญประกาศ (`'`), คำสั่ง SQL, หรือคอมเมนต์ (`--`) เข้าไปได้ ค่าเหล่านั้นอาจถูกตีความเป็น **ไวยากรณ์ของ SQL** ไม่ใช่แค่ตัวอักษรในชื่อเมนู

ผลที่ตามมาในทางหลักการมีได้หลายระดับ เช่น

- เงื่อนไข `WHERE` ไม่ทำงานตามที่ผู้พัฒนาตั้งใจ (ดึงข้อมูลเกินสิทธิ์ที่หน้าจอควรเห็น)
- โครงสร้างคำสั่งถูกเปลี่ยน (เช่น ต่อเป็นคำสั่งชุดอื่น หรือต่อผลลัพธ์ด้วย `UNION`)
- หากบัญชีที่ใช้ต่อฐานข้อมูลมีสิทธิ์เกินจำเป็น ความเสียหายจะกว้างขึ้น

หลักคิดที่สำคัญที่สุดมีแค่ข้อเดียว:

> **ข้อมูลจากผู้ใช้ต้องเป็น “ค่า” (value) เท่านั้น ห้ามกลายเป็น “คำสั่ง” (SQL syntax)**

วิธีมาตรฐานคือใช้ **parameterized query / prepared statement** ให้ไดรเวอร์ส่งคำสั่งกับค่าแยกกัน

## 2. ตัวอย่างโค้ด “เขียนไม่ดี” (VULNERABLE)

สมมติว่าเราจะเพิ่มฟีเจอร์ **ค้นหาเมนูตามชื่อ** ให้แอปสั่งอาหาร ซึ่งแอปจริงใน US-101 ยังไม่มีฟีเจอร์นี้ — ตัวอย่างด้านล่างจึงเป็นโจทย์สมมติเพื่อการสอน ไม่ใช่โค้ดที่อยู่ใน Production

### 2.1 ฝั่ง Node.js / Express + raw SQL (จุดช่องโหว่หลัก)

ดูไฟล์ `vulnerable_example.js` ทั้งไฟล์ จุดที่เป็นปัญหาคือการต่อสตริงแบบนี้:

```javascript
// ไม่ปลอดภัย: นำค่าจากผู้ใช้มาต่อในสตริง SQL โดยตรง
app.get("/api/menu/search", async (req, res) => {
  const q = req.query.q ?? "";
  const sql = `
    SELECT id, name, price, category, image_url, is_available
    FROM menu_items
    WHERE is_available = true
      AND name ILIKE '%${q}%'
    ORDER BY sort_order ASC, id ASC
  `;
  const result = await pool.query(sql);
  res.json(result.rows);
});
```

ปัญหาอยู่ที่ `` name ILIKE '%${q}%' `` ค่า `q` มาจาก `req.query.q` ซึ่งผู้ใช้กำหนดเองได้ทั้งก้อน แล้วถูกแทรกเข้าไปในคำสั่ง SQL ก่อนส่งให้ฐานข้อมูล

### 2.2 รูปแบบ string-built query อีกแบบ (ไม่ปลอดภัยเช่นกัน)

บางครั้งไม่ได้ใช้ template string แต่ต่อด้วยตัวดำเนินการ `+` หรือรับเงื่อนไขทั้งก้อนจากผู้ใช้ ผลลัพธ์เหมือนกัน คือผู้ใช้เขียน SQL แทนผู้พัฒนาได้:

```javascript
// ไม่ปลอดภัยเช่นกัน: ต่อสตริงด้วย + 
const sql =
  "SELECT id, name, price, category, is_available " +
  "FROM menu_items WHERE is_available = true AND name ILIKE '%" +
  req.query.q +
  "%'";

// ไม่ปลอดภัยยิ่งกว่า: ให้ผู้ใช้ส่งเงื่อนไข WHERE ทั้งก้อน
const sql = "SELECT id, name, price FROM menu_items WHERE " + req.query.filter;
```

ไม่ว่าจะเขียนด้วย `` `${q}` ``, การต่อ `+`, หรือ `sql.concat(...)` หลักการผิดเหมือนกัน: **ไวยากรณ์ SQL ถูกประกอบตอนรันจากข้อมูลที่ผู้ใช้ควบคุมได้**

## 3. อธิบายทีละขั้นว่าทำไมโค้ดนี้พัง

ใช้คำสั่งจากข้อ 2.1 เป็นหลัก เมื่อแอปต้องการค้นหา โปรแกรมจะสร้าง SQL แล้วส่งไปทั้งก้อน

### 3.1 กรณีปกติ (ผู้ใช้ค้นหาชื่อเมนูจริง)

ผู้ใช้พิมพ์: `ข้าว`

SQL ที่ถูกสร้างขึ้น:

```sql
SELECT id, name, price, category, image_url, is_available
FROM menu_items
WHERE is_available = true
  AND name ILIKE '%ข้าว%'
ORDER BY sort_order ASC, id ASC
```

ความหมายตรงตามที่ตั้งใจ: เลือกเฉพาะเมนูที่ **มีขาย** (`is_available = true`) และชื่อมีคำว่า “ข้าว”

### 3.2 อินพุตที่เปลี่ยนเงื่อนไขให้เป็นจริงเสมอ

ผู้ใช้พิมพ์: `' OR '1'='1' --`

สตริงที่ถูกแทรกเข้าไปทำให้ SQL กลายเป็น:

```sql
SELECT id, name, price, category, image_url, is_available
FROM menu_items
WHERE is_available = true
  AND name ILIKE '%' OR '1'='1' --%'
ORDER BY sort_order ASC, id ASC
```

อ่านทีละส่วน

| ส่วน | เกิดอะไรขึ้น |
| --- | --- |
| `name ILIKE '%'` | เครื่องหมาย `'` ที่ผู้ใช้พิมพ์ **ปิดสตริง** ของ `ILIKE` ก่อนเวลา |
| `OR '1'='1'` | ต่อเงื่อนไขที่เป็นจริงเสมอ (`'1'` เท่ากับ `'1'`) |
| `--` | คือคอมเมนต์ของ SQL ทำให้ข้อความที่เหลือในบรรทัด (เช่น `'%'` ที่โค้ดเติมท้าย) ไม่มีผล |
| ลำดับความสำคัญของตัวดำเนินการ | `AND` ผูกแน่นกว่า `OR` ดังนั้นเงื่อนไขจริง ๆ คือ `(is_available = true AND name ILIKE '%') OR ('1'='1')` |

เพราะ `'1'='1'` เป็นจริงเสมอ **ทั้งแถวในตารางจึงผ่านเงื่อนไข** รวมถึงเมนูที่ตั้งใจซ่อนไว้ด้วย `is_available = false` (ใน US-101 เมนูที่หมด/งดขายต้องไม่โชว์บนหน้าเว็บ)

บทเรียน: ผู้ใช้ไม่ได้ “ค้นหาชื่อเมนู” อีกต่อไป แต่ **แก้โครงสร้างเงื่อนไข** ของคำสั่งได้

### 3.3 อินพุตที่ปิดสตริงแล้วจบคำสั่ง

ผู้ใช้พิมพ์: `'; --`

SQL ที่ถูกสร้างขึ้นมีลักษณะแบบนี้:

```sql
SELECT id, name, price, category, image_url, is_available
FROM menu_items
WHERE is_available = true
  AND name ILIKE '%'; --%'
ORDER BY sort_order ASC, id ASC
```

เครื่องหมาย `;` ใน SQL ใช้จบคำสั่ง ส่วน `--` ทำให้ส่วนที่เหลือเป็นคอมเมนต์ จุดสอนคือ: ถ้าอินพุตไปอยู่ในสตริง SQL ได้ ผู้ใช้ไม่ได้ถูกจำกัดอยู่แค่ “ค่าในเครื่องหมายคำพูด” อีกต่อไป

หากไดรเวอร์หรือฐานข้อมูลยอมให้รันหลายคำสั่งในครั้งเดียว ผู้ไม่หวังดีอาจต่อคำสั่งอื่นต่อท้ายได้ นี่คือเหตุผลที่ต้อง

- ใช้ parameterized query (ค่าถูกส่งแยกจากคำสั่ง จึงไม่กลายเป็น `;` หรือ `--` ในไวยากรณ์)
- ตั้งค่าไม่ให้รันหลายคำสั่งในหนึ่งเรียกถ้าไลบรารีมีตัวเลือกนั้น
- ให้บัญชีฐานข้อมูลมีสิทธิ์น้อยที่สุด (เช่น `SELECT` อย่างเดียว)

> บทเรียนนี้ **ไม่สาธิตคำสั่งทำลายข้อมูล** และห้ามทดลองต่อคำสั่งเพิ่มกับฐานข้อมูลจริง

### 3.4 อินพุตที่ต่อผลลัพธ์ด้วย UNION

ผู้ใช้พิมพ์: `' UNION SELECT id, name, price, category, image_url, is_available FROM menu_items --`

SQL ที่ถูกสร้างขึ้นมีลักษณะแบบนี้:

```sql
SELECT id, name, price, category, image_url, is_available
FROM menu_items
WHERE is_available = true
  AND name ILIKE '%' UNION SELECT id, name, price, category, image_url, is_available FROM menu_items --%'
ORDER BY sort_order ASC, id ASC
```

`UNION` รวมผลลัพธ์ของสองคำสั่ง `SELECT` คำสั่งแรกยังมี `WHERE is_available = true` แต่คำสั่งหลัง (ที่ถูกแทรกเข้ามา) **ไม่ติดเงื่อนไขนั้น** จึงดึงเมนูทั้งหมดรวมรายการที่ควรซ่อน

ข้อคิดเพิ่ม: ถ้าบัญชีที่แอปใช้ต่อฐานข้อมูลมีสิทธิ์อ่านตารางอื่นได้ด้วย ผู้ไม่หวังดีอาจใช้แนวทางเดียวกันเพื่อดึงข้อมูลนอกตารางเมนู ดังนั้นนอกจากการผูกพารามิเตอร์แล้ว ต้องใช้ **least privilege** ด้วย — แอปหน้าร้านไม่ควรมีสิทธิ์เกิน `SELECT` บนตารางที่จำเป็น

## 4. ตัวอย่างโค้ด “เขียนถูก” (SECURE)

หลักการแก้คือแยก “คำสั่ง” กับ “ค่า” จากกัน ดูไฟล์ `secure_example.js` สำหรับตัวอย่างครบชุด

### 4.1 Parameterized query / prepared statement (Node.js + `pg`)

```javascript
app.get("/api/menu/search", async (req, res) => {
  const q = (req.query.q ?? "").trim();

  if (!q) {
    return res.status(400).json({ error: "กรุณาระบุคำค้นหา" });
  }
  if (q.length > 100) {
    return res.status(400).json({ error: "คำค้นหายาวเกินไป" });
  }

  // ปลอดภัย: $1 คือพารามิเตอร์ ค่าของ q ถูกส่งแยก ไม่กลายเป็นไวยากรณ์ SQL
  const sql = `
    SELECT id, name, price, category, image_url, is_available
    FROM menu_items
    WHERE is_available = true
      AND name ILIKE '%' || $1 || '%'
    ORDER BY sort_order ASC, id ASC
  `;
  const result = await pool.query(sql, [q]);
  res.json(result.rows);
});
```

ถ้าผู้ใช้พิมพ์ `' OR '1'='1' --` ฐานข้อมูลจะค้นหาเมนูที่ชื่อมีตัวอักษรเหล่านั้นตามตัวอักษร จะ **ไม่** ปิดสตริง ไม่เพิ่ม `OR` และไม่เปิดคอมเมนต์

เทียบให้เห็นภาพ:

| แบบเขียน | สิ่งที่ฐานข้อมูลรับ |
| --- | --- |
| ไม่ปลอดภัย: ต่อสตริงเอง | คำสั่งก้อนเดียวที่ผู้ใช้ช่วยเขียนไวยากรณ์ได้ |
| ปลอดภัย: `ILIKE '%' \|\| $1 \|\| '%'` + `[q]` | แม่แบบคำสั่งคงที่ + ค่าของ `$1` ส่งแยกต่างหาก |

### 4.2 ใช้ Supabase / PostgREST client (ผูกค่าให้ ไม่ต่อ SQL เอง)

แอป US-101 บน Production ดึงเมนูผ่าน PostgREST โดยไม่นำอินพุตผู้ใช้ไปประกอบเป็น raw SQL ซึ่งเป็นแนวทางที่ถูกต้อง ถ้ายืนตัวอย่างค้นหาด้วย client ทางการ จะเขียนได้แบบนี้:

```javascript
import { createClient } from "@supabase/supabase-js";

const supabase = createClient(process.env.SUPABASE_URL, process.env.SUPABASE_ANON_KEY);

const { data, error } = await supabase
  .from("menu_items")
  .select("id, name, price, category, image_url, is_available")
  .eq("is_available", true)
  .ilike("name", `%${q}%`)
  .order("sort_order", { ascending: true })
  .order("id", { ascending: true });
```

เมธอด `.eq()` และ `.ilike()` ส่งค่าเป็นพารามิเตอร์ของ API ไม่ใช่การต่อคำสั่ง SQL เอง ห้ามย้อนกลับไปสร้าง URL หรือ SQL ด้วยการต่อสตริงจาก `q` เช่น

```javascript
// ไม่ปลอดภัย: ต่อสตริงเองทั้งที่เป็น PostgREST
const url = `${SUPABASE_URL}/rest/v1/menu_items?name=ilike.*${q}*`;
```

### 4.3 มาตรการเสริม (ทำควบคู่ ไม่ใช่ตัวแทน parameterized query)

1. **ตรวจค่าอินพุต (input validation)** — จำกัดความยาว ตรวจชนิดข้อมูล ตัดช่องว่าง ส่วนรูปแบบอักขระใช้เป็นชั้นเพิ่ม ไม่ใช่การป้องกันหลัก เพราะชื่อเมนูอาจมีเครื่องหมายที่กรองยาก และการกรองสตริงเองมักมีช่องโหว่เหลือ
2. **Least privilege** — บัญชีที่แอปใช้ควร `SELECT` ได้เฉพาะตารางที่ต้องใช้ ไม่ควรมีสิทธิ์ `INSERT` / `UPDATE` / `DELETE` / `DROP` ถ้าหน้าร้านไม่จำเป็น (US-101 เป็นแอปอ่านเมนูและสรุปตะกร้าในหน่วยความจำ ไม่เขียนกลับฐานข้อมูล)
3. **ไม่เปิด raw SQL ให้ผู้ใช้** — ห้ามรับประโยค SQL, ชิ้นส่วน `WHERE`, หรือชื่อคอลัมน์จากผู้ใช้แล้วไปต่อในคำสั่ง ถ้าต้องเรียงลำดับตามคอลัมน์ ให้ใช้ **allowlist** เช่น รับได้เฉพาะ `"name"` หรือ `"price"` แล้วเลือกข้อความ `ORDER BY` จากในโค้ดเอง
4. **ไม่ใส่รหัสลับฝั่งเบราว์เซอร์เกินความจำเป็น** — ใช้คีย์แบบ anon/publishable ที่ถูกจำกัดด้วย RLS ไม่ใช้ service role / รหัสผ่านฐานข้อมูลบนหน้าเว็บ

## 5. ตารางสรุป: ช่องโหว่ → ความเสี่ยง → วิธีแก้

| ช่องโหว่ / วิธีเขียนผิด | ความเสี่ยง | วิธีแก้ |
| --- | --- | --- |
| ต่อค่าค้นหาเข้า `WHERE ... ILIKE '%${q}%'` | ผู้ใช้เปลี่ยนเงื่อนไขได้ ดึงเมนูที่ควรซ่อน หรือข้อมูลเกินกว่าที่ค้นหา | ใช้พารามิเตอร์ เช่น `ILIKE '%' \|\| $1 \|\| '%'` แล้วส่ง `[q]` แยก |
| ต่อสตริงด้วย `+` หรือรับ `WHERE` ทั้งก้อนจากผู้ใช้ | เหมือนกัน หรือเปิดให้เขียนเงื่อนไขอิสระทั้งประโยค | ห้ามประกอบ SQL จากอินพุต กำหนดเงื่อนไขในโค้ดแล้วผูกค่าด้วยพารามิเตอร์ |
| ต่อสตริงใน `ORDER BY ${sort}` หรือชื่อตาราง/คอลัมน์ | ผู้ใช้เปลี่ยนโครงสร้างคำสั่งได้แม้ค่าใน `WHERE` จะถูกผูกพารามิเตอร์แล้ว | ใช้ allowlist ของชื่อคอลัมน์ที่อนุญาต แล้วเลือกข้อความ SQL จากในโค้ด |
| บัญชีฐานข้อมูลสิทธิ์กว้างเกิน | หากมีช่องโหว่ ผลกระทบขยายจากการอ่านข้อมูลเกิน ไปถึงการแก้ไขหรือทำลายข้อมูล | ให้สิทธิ์เท่าที่จำเป็น (หน้าร้าน: `SELECT` บนตารางเมนู) + RLS |
| เปิด raw SQL / service role ให้ฝั่งผู้ใช้ | ผู้ใช้ข้ามชั้น API ไปคุยกับฐานข้อมูลโดยตรงได้ | ให้ผ่าน API/client ที่ผูกพารามิเตอร์ และใช้คีย์ที่จำกัดสิทธิ์ |

## 6. แบบฝึกหัดสำหรับนักศึกษา

ทำบนกระดาษหรือแก้ในสำเนาไฟล์ตัวอย่าง **ห้ามชี้ไปที่ฐานข้อมูล Production**

### ข้อ 1 — หาช่องโหว่

ดูโค้ดต่อไปนี้ แล้วตอบ: (ก) ช่องโหว่อยู่บรรทัดใด (ข) ทำไมจึงไม่ปลอดภัย (ค) ถ้าผู้ใช้ควบคุมค่า `category` ได้ เงื่อนไข `is_available = true` อาจไม่ทำงานตามตั้งใจได้อย่างไร (อธิบายหลักการ ไม่ต้องไปทดลองกับระบบจริง)

```javascript
app.get("/api/menu", async (req, res) => {
  const category = req.query.category;
  const sql = `
    SELECT id, name, price, category
    FROM menu_items
    WHERE is_available = true
      AND category = '${category}'
  `;
  const { rows } = await pool.query(sql);
  res.json(rows);
});
```

### ข้อ 2 — แก้โค้ด

เขียนเวอร์ชันที่ปลอดภัยของข้อ 1 ด้วย parameterized query และเพิ่มการตรวจค่าเบื้องต้นที่เหมาะสม (เช่น ต้องมีค่า, จำกัดความยาว)

### ข้อ 3 — ชี้ว่าอันใดปลอดภัย และอย่าพลาดจุดบอด

โค้ดสองชุดด้านล่าง ชุดใดปลอดภัยจาก SQL Injection ชุดใดไม่ปลอดภัย เพราะอะไร

```javascript
// ชุด A
const sort = req.query.sort;
const sql = `
  SELECT id, name, price
  FROM menu_items
  WHERE is_available = true
    AND name ILIKE '%' || $1 || '%'
  ORDER BY ${sort}
`;
await pool.query(sql, [req.query.q]);

// ชุด B
const { data, error } = await supabase
  .from("menu_items")
  .select("id, name, price")
  .eq("is_available", true)
  .ilike("name", `%${req.query.q}%`);
```

## 7. เฉลยย่อ

**ข้อ 1.** (ก) บรรทัดที่ประกอบ `sql` โดยใส่ `'${category}'` ลงในคำสั่งโดยตรง (ข) ค่าจากผู้ใช้กลายเป็นไวยากรณ์ SQL ได้ ไม่ใช่แค่ข้อความหมวดหมู่ (ค) ผู้ใช้สามารถปิดเครื่องหมายคำพูดก่อนเวลา แล้วต่อเงื่อนไข `OR` ที่เป็นจริงเสมอ หรือใส่คอมเมนต์ตัดส่วนที่เหลือ ทำให้เงื่อนไข `is_available = true` ถูกข้ามหรือถูกลดความหมาย ด้วยลำดับ `AND`/`OR` แบบเดียวกับที่อธิบายในหัวข้อ 3.2

**ข้อ 2.** ตัวอย่างคำตอบที่ถูกต้องในหลักการ:

```javascript
app.get("/api/menu", async (req, res) => {
  const category = (req.query.category ?? "").trim();
  if (!category || category.length > 50) {
    return res.status(400).json({ error: "หมวดหมู่ไม่ถูกต้อง" });
  }
  const sql = `
    SELECT id, name, price, category
    FROM menu_items
    WHERE is_available = true
      AND category = $1
  `;
  const { rows } = await pool.query(sql, [category]);
  res.json(rows);
});
```

การตรวจค่าเป็นชั้นเสริม การแก้หลักคือ `category = $1` และส่งค่าในอาเรย์พารามิเตอร์

**ข้อ 3.** ชุด A **ไม่ปลอดภัย** แม้จะผูก `$1` สำหรับคำค้นหาแล้ว เพราะ `ORDER BY ${sort}` ยังต่อสตริงจากผู้ใช้ ชื่อคอลัมน์หรือชิ้นส่วน SQL ใน `ORDER BY` ไม่ใช่ค่าที่จะผูกด้วย `$1` ได้ตามปกติ ต้องใช้ allowlist เช่น อนุญาตเฉพาะ `name` กับ `price` แล้วเลือกข้อความในโค้ดเอง ชุด B **ปลอดภัยจาก SQL Injection ในแง่การค้นหาชื่อ** เพราะใช้ client ของ Supabase ส่งค่าผ่าน `.eq()` / `.ilike()` ไม่ต่อ raw SQL เอง (ยังควรจำกัดความยาวของ `q` เป็นชั้นเสริม)

## 8. สิ่งที่แอป Production ของวิชานี้ทำถูกแล้ว (สรุปสั้น ๆ)

แอป Office Food Ordering US-101 เวอร์ชันที่ Deploy แล้ว (v1.0.2) **ไม่ได้มีจุดค้นหาแบบต่อ SQL** ตามตัวอย่างช่องโหว่ในบทนี้ หน้าเว็บดึงเมนูผ่าน PostgREST ด้วยตัวกรองคงที่ เช่น `is_available=eq.true` ไม่นำอินพุตจากผู้ใช้ไปประกอบเป็น raw SQL ตะกร้าเก็บในหน่วยความจำของหน้าเว็บ ไม่เขียนกลับฐานข้อมูล และบัญชีฝั่งผู้ใช้ถูกออกแบบให้อ่านเมนูเท่าที่จำเป็น
