# UC02 เข้าสู่ระบบด้วย Social Login (Office Food Ordering)
Version: req v1.0 (2026-11-21) | Owner: 201 BA | Status: In Progress

## User Story
ในฐานะ พนักงานในออฟฟิศ ฉันต้องการ เข้าสู่ระบบด้วย Social Login เพื่อ ยืนยันตัวตนก่อนยืนยันคำสั่งซื้อและดูประวัติการสั่งซื้อ โดยยังสามารถท่องเมนูได้โดยไม่ต้องล็อกอิน

## ขอบเขต (ทำเท่านี้เท่านั้น)
- มีปุ่มข้อความ **เข้าสู่ระบบด้วย Google**
- ล็อกอินด้วย Supabase Auth (project ref `yhcjsgbffgabsmsybnle`) ตามกติกาผู้ให้บริการในเอกสารนี้
- หลังล็อกอินสำเร็จ แสดงชื่อและ/หรืออีเมลของผู้ใช้ และมีปุ่มออกจากระบบ
- ท่องเมนูและใช้สรุปรายการตาม US-101 ได้โดยไม่ต้องล็อกอิน (US-101 ต้องไม่พัง)
- การยืนยันสั่งซื้อและการดูประวัติการสั่งซื้อทำได้เฉพาะเมื่อล็อกอินแล้ว
- ออกจากระบบแล้วเซสชันต้องสิ้นสุดจริง
- ตั้งค่า credential และการทดสอบความปลอดภัยตามมาตรฐานที่กำหนดในเอกสารนี้
- มีบัญชี mockup อย่างน้อย 2 บัญชี (user A, user B) สำหรับทดสอบ

## นอกขอบเขต
- เปิดให้สมัครด้วยอีเมลด้วยตนเอง (ต้องคงปิดตาม ACT-05)
- ชำระเงิน
- ยืนยัน/บันทึกคำสั่งซื้อ และหน้าประวัติการสั่งซื้อ (อยู่ใน UC03 แต่ต้องกันไม่ให้ทำได้ถ้ายังไม่ล็อกอิน)
- จัดการผู้ใช้แบบผู้ดูแลระบบ, แก้ไขโปรไฟล์, ลบบัญชี, รีเซ็ตรหัสผ่านแบบบริการผู้ใช้ทั่วไป
- ผู้ให้บริการ OAuth นอกลำดับกติกาที่กำหนด
- เปลี่ยนพฤติกรรมเมนูหรือตะกร้าของ US-101 (รวม BA-C1, BA-C2)
- เปลี่ยนข้อมูลเมนู baseline (12 แถว / 10 available / รวมทุกเมนู available อย่างละ 1 = 1,781.25)

## Acceptance Criteria
- AC1 หน้าเว็บมีปุ่มข้อความ "เข้าสู่ระบบด้วย Google"
- AC2 ผู้ใช้ที่ยังไม่ล็อกอินท่องเมนู เลือกอาหาร และดูสรุปรายการได้ครบตาม US-101 (req v1.1) โดยไม่บังคับล็อกอิน และพฤติกรรมเดิมไม่พัง
- AC3 การยืนยันสั่งซื้อและการดูประวัติการสั่งซื้อทำได้เฉพาะเมื่อล็อกอินแล้ว หากยังไม่ล็อกอิน ระบบต้องไม่บันทึกออเดอร์ ไม่แสดงประวัติของผู้อื่นหรือของตนเอง และต้องนำผู้ใช้ไปล็อกอินหรือแจ้งให้ล็อกอิน
- AC4 หลังล็อกอินสำเร็จ แสดงชื่อและ/หรืออีเมลของผู้ใช้ที่ล็อกอินอยู่ และมีปุ่มออกจากระบบ
- AC5 กดออกจากระบบแล้วเซสชันสิ้นสุดจริง: กด Back ของเบราว์เซอร์ หรือรีเฟรชหน้า ต้องยังคงสถานะออกจากระบบ ไม่สามารถกลับเข้าสู่เซสชันเดิมได้โดยไม่ล็อกอินใหม่
- AC6 การล็อกอินใช้มาตรฐาน OAuth 2.0 พร้อม PKCE
- AC7 Redirect URL อยู่ใน allowlist เฉพาะโดเมนของแอปนี้: `https://vibecode-office-food.vercel.app` และ Vercel Preview ของโปรเจกต์นี้เท่านั้น การส่ง `redirect_uri` ไปโดเมนอื่นต้องถูกปฏิเสธ
- AC8 ฝั่ง client ต้องไม่มี secret และไม่มี `service_role` key
- AC9 หลัง callback สำเร็จ ต้องไม่มี token ค้างใน URL (ทั้ง query และ hash)
- AC10 CSP ถูกอัปเดตเฉพาะโดเมนที่จำเป็นต่อการล็อกอินและเรียก Auth เท่านั้น ห้ามเปิดโดเมนที่ไม่จำเป็น
- AC11 การสมัครด้วยอีเมลด้วยตนเองยังปิดอยู่ตาม ACT-05 (`disable_signup: true`) ทั้งเมื่อใช้ Google/GitHub และเมื่อใช้ทางสำรอง Email+Password
- AC12 ผู้ให้บริการล็อกอินที่ใช้งานจริงเป็นไปตามกติกาลำดับในส่วนกติกา หากใช้ทางสำรอง Email+Password ปุ่ม "เข้าสู่ระบบด้วย Google" ยังคงมีและถูกเชื่อมไว้พร้อมใช้เมื่อเจ้าของใส่ credentials
- AC13 มีบัญชีทดสอบ mockup อย่างน้อย 2 บัญชี (user A และ user B) ใช้แยกเซสชันและทดสอบการแบ่งข้อมูลข้ามผู้ใช้ได้
- AC14 204 ทดสอบความปลอดภัยตาม OWASP ASVS L1 ส่วน V2, V3, V4 และชุดตรวจ OAuth ตามส่วนความต้องการด้านความปลอดภัย ผลตรวจต้องผ่านเกณฑ์ที่ระบุ หรือบันทึกข้อยกเว้นให้ 201 BA ยอมรับเป็นลายลักษณ์อักษร
- AC15 การทดสอบแบบ active บนสภาพแวดล้อม mockup ทำได้ แต่ห้ามใช้คำสั่ง `DROP`, `TRUNCATE`, `ALTER` และหลังมีการเขียนข้อมูลต้องคืน baseline

- ออกจากระบบต้องสิ้นสุดเซสชันจริง ใช้ Back หรือรีเฟรชแล้วกลับเข้าสู่ระบบเดิมไม่ได้

## ความต้องการด้านความปลอดภัย
- ใช้ OAuth 2.0 + PKCE
- Allowlist ของ Redirect URL จำกัดเฉพาะโดเมนของเรา: `https://vibecode-office-food.vercel.app` และ Vercel Preview ของโปรเจกต์นี้
- ห้ามมี secret หรือ `service_role` key ฝั่ง client (ใช้ได้เฉพาะ publishable/anon key ตามแนว US-101)
- หลัง callback ห้ามเหลือ token ใน URL
- อัปเดต CSP เฉพาะโดเมนที่จำเป็น
- คง `disable_signup: true` ตาม ACT-05 ไม่เปิดการสมัครเองแม้ใช้ทางสำรอง Email+Password
- ให้ 204 ทดสอบตาม OWASP ASVS L1 หมวด V2 Authentication, V3 Session Management, V4 Access Control และตรวจเพิ่มด้าน OAuth ดังนี้: `state`/PKCE, `redirect_uri` tampering, open redirect, token leakage, session fixation, logout invalidation, JWT signature/expiry, cross-user IDOR
- การทดสอบแบบ active บน mockup ทำได้ แต่ห้าม `DROP` / `TRUNCATE` / `ALTER` และต้องคืน baseline หลังมีการเขียนข้อมูล
