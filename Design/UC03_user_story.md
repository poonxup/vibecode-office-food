# UC03 ประวัติการสั่งซื้อ (Office Food Ordering)
Version: req v1.0 (2026-11-21) | Owner: 201 BA | Status: In Progress

## User Story
ในฐานะ พนักงานในออฟฟิศที่ล็อกอินแล้ว ฉันต้องการ ยืนยันคำสั่งซื้อจากสรุปรายการ และดูประวัติการสั่งซื้อของตนเอง เพื่อ บันทึกออเดอร์ได้ ตรวจสอบรายการที่เคยสั่ง และมั่นใจว่าเห็นเฉพาะข้อมูลของตนเอง

## ขอบเขต (ทำเท่านี้เท่านั้น)
- มีปุ่มข้อความ **ยืนยันสั่งซื้อ** ในสรุปรายการสั่ง
- ปุ่มนี้ต้องล็อกอินก่อนใช้ และถูกปิดเมื่อตะกร้าว่าง
- กดยืนยันแล้วระบบบันทึกคำสั่งซื้อ ล้างตะกร้า และแสดงข้อความสำเร็จ
- มีหน้าประวัติการสั่งซื้อ เรียงจากใหม่ไปเก่า แสดงวันเวลา (Asia/Bangkok) รายการ จำนวน ราคาต่อหน่วย และยอดรวมบิล (รูปแบบตาม BA-C1 เช่น 1,250.00)
- กดที่บิลแล้วดูรายละเอียดของบิลนั้นได้ และมีข้อความสถานะว่างเมื่อยังไม่มีประวัติ
- ผู้ใช้เห็นเฉพาะคำสั่งซื้อของตนเอง ทั้งใน UI และผ่าน REST โดยใช้ RLS บน `auth.uid()`
- ราคาและยอดรวมคำนวณในฐานข้อมูลจากราคาเมนูจริง มีการ snapshot ชื่อและราคา ณ เวลาที่สั่ง ฝั่ง client แก้ไขราคาไม่ได้ และรายการที่ `is_available = false` สั่งไม่ได้
- บันทึกผ่าน RPC เท่านั้น และ role `anon` เข้าถึงข้อมูลคำสั่งซื้อไม่ได้
- ต้องไม่เปลี่ยนข้อมูลเมนู baseline ของ US-101

## นอกขอบเขต
- ชำระเงิน
- ยกเลิก แก้ไข หรือลบคำสั่งซื้อหลังจากบันทึกแล้ว
- ผู้ดูแลระบบดูหรือจัดการคำสั่งซื้อของทุกคน
- การคงตะกร้าหลังรีเฟรชหน้า (ยังเป็นไปตาม BA-C2 ของ US-101: ตะกร้าอยู่ใน state ของเบราว์เซอร์ รีเฟรชแล้วล้าง)
- ระบบล็อกอินเอง (อยู่ใน UC02 แต่ UC03 ต้องพึ่งพาและบังคับให้ล็อกอินก่อนยืนยัน/ดูประวัติ)
- เปลี่ยนข้อมูลเมนู baseline (12 แถว / 10 available / รวมทุกเมนู available อย่างละ 1 = 1,781.25)
- เปิดสิทธิ์ให้ `anon` อ่านหรือเขียน `orders` / `order_items`

## Acceptance Criteria
- AC1 ในสรุปรายการสั่งมีปุ่มข้อความ "ยืนยันสั่งซื้อ"
- AC2 เมื่อตะกร้าว่าง ปุ่ม "ยืนยันสั่งซื้อ" อยู่ในสถานะ disabled กดแล้วไม่บันทึกคำสั่งซื้อ
- AC3 การยืนยันสั่งซื้อและการดูประวัติต้องล็อกอินแล้วตาม UC02 หากยังไม่ล็อกอิน ระบบต้องไม่บันทึกคำสั่งซื้อ และไม่แสดงประวัติ
- AC4 เมื่อล็อกอินแล้วและตะกร้ามีสินค้า กด "ยืนยันสั่งซื้อ" แล้วระบบบันทึกคำสั่งซื้อสำเร็จ ล้างตะกร้ากลับเป็นว่างตาม US-101 (ยอดรวม 0.00) และแสดงข้อความสำเร็จ
- AC5 มีหน้าประวัติการสั่งซื้อ เรียงจากใหม่ไปเก่า (newest to oldest) ตาม `created_at`
- AC6 แต่ละบิลแสดงวันเวลาในโซน Asia/Bangkok, รายการสินค้า, จำนวน (`qty`), ราคาต่อหน่วย และยอดรวมบิล โดยรูปแบบราคาเป็นทศนิยม 2 ตำแหน่ง มีคอมมาคั่นหลักพัน ตาม BA-C1 เช่น 1,250.00
- AC7 กดที่บิลหนึ่งรายการแล้วแสดงรายละเอียดของบิลนั้น (รายการ, จำนวน, ราคาต่อหน่วย, ยอดรวมบรรทัด, ยอดรวมบิล, วันเวลา)
- AC8 เมื่อผู้ใช้ที่ล็อกอินแล้วยังไม่มีคำสั่งซื้อ หน้าประวัติแสดงข้อความสถานะว่าง (empty-state)
- AC9 ผู้ใช้เห็นเฉพาะคำสั่งซื้อของตนเองทั้งใน UI และเมื่อเรียก REST โดยบังคับด้วย RLS บน `auth.uid()` ผู้ใช้ A ต้องไม่เห็นหรือดึงออเดอร์ของ user B ได้ (cross-user IDOR ต้องถูกกัน)
- AC10 ราคาต่อหน่วยและยอดรวมคำนวณในฐานข้อมูลจากราคาจริงใน `menu_items` ฝั่ง client ส่งราคาเองหรือแก้ราคาก่อนบันทึกไม่ได้ หากส่งราคาที่ต่างจากฐานข้อมูล ระบบต้องปฏิเสธหรือละเลยราคาจาก client แล้วใช้ราคาในฐานข้อมูล
- AC11 ชื่อและราคาถูก snapshot ตอนสั่งใน `name_snapshot` และ `unit_price_snapshot` การเปลี่ยนชื่อหรือราคาเมนูภายหลังต้องไม่เปลี่ยนประวัติที่บันทึกแล้ว
- AC12 รายการที่ `is_available = false` สั่งไม่ได้ ทั้งจาก UI และจากการเรียก RPC/REST โดยตรง
- AC13 การเพิ่มคำสั่งซื้อทำได้ผ่าน RPC เท่านั้น ห้ามให้ client `INSERT` ตรงลง `orders` หรือ `order_items` และ role `anon` ต้องไม่มีสิทธิ์เข้าถึงทั้งสองตาราง
- AC14 ข้อมูลเมนู baseline ต้องไม่เปลี่ยน: `menu_items` มี 12 แถว, 10 รายการ available, รวมราคาทุกเมนู available อย่างละ 1 เท่ากับ 1,781.25

## ข้อมูลที่ใช้
- ตาราง `orders`: `id`, `user_id`, `created_at`, `total`, `status`
- ตาราง `order_items`: `order_id`, `menu_item_id`, `name_snapshot`, `unit_price_snapshot`, `qty`, `line_total`
- การบันทึกคำสั่งซื้อทำผ่าน RPC เท่านั้น (ชื่อฟังก์ชันให้ 202 กำหนดแล้วบันทึกใน Data Model)
- role `anon` ไม่มีสิทธิ์เข้าถึง `orders` และ `order_items`
- อ้างอิงราคาและสถานะสินค้าจาก `menu_items` ที่มีอยู่ (US-101) แต่ห้ามเปลี่ยนข้อมูลเมนู baseline: 12 แถว / 10 available / 1,781.25
- ใช้บัญชี mockup อย่างน้อย 2 บัญชีจาก UC02 (user A, user B) เพื่อตรวจว่าแต่ละคนเห็นเฉพาะออเดอร์ของตนเอง
- ตะกร้าก่อนยืนยันยังเก็บใน state ของเบราว์เซอร์ตาม BA-C2 ไม่บันทึกตะกร้าลงฐานข้อมูล

## กติกา
- ปุ่ม "ยืนยันสั่งซื้อ" อยู่ที่สรุปรายการสั่ง ต้องล็อกอินก่อนใช้ และถูกปิดเมื่อตะกร้าว่าง
- กดยืนยันสำเร็จแล้วต้องบันทึกคำสั่งซื้อ ล้างตะกร้า และแสดงข้อความสำเร็จ
- ประวัติเรียงจากใหม่ไปเก่า วันเวลาแสดงในโซน Asia/Bangkok
- รูปแบบราคาตาม BA-C1: ทศนิยม 2 ตำแหน่งเสมอ มีคอมมาคั่นหลักพัน เช่น 1,250.00 ใช้กับราคาต่อหน่วย ยอดรวมบรรทัด และยอดรวมบิล
- `line_total` และ `total` คำนวณในฐานข้อมูล จากราคาเมนูจริง ณ เวลาที่สั่ง ไม่ใช้ราคาที่ client ส่งมาเป็นแหล่งความจริง
- ชื่อและราคาต้องถูก snapshot ใน `name_snapshot` และ `unit_price_snapshot` ณ เวลาที่สั่ง
- รายการที่ `is_available = false` สั่งไม่ได้
- ผู้ใช้เห็นเฉพาะแถวที่ `orders.user_id = auth.uid()` ทั้ง UI และ REST
- การเพิ่มข้อมูลคำสั่งซื้อผ่าน RPC เท่านั้น; `anon` ไม่มีสิทธิ์เข้าถึง
- ต้องไม่เปลี่ยนข้อมูลเมนู baseline (12 แถว / 10 available / 1,781.25)

## ความต้องการด้านความปลอดภัย
- เปิด RLS บน `orders` และ `order_items` และจำกัดให้ผู้ใช้เข้าถึงได้เฉพาะแถวของตนเองผ่าน `auth.uid()`
- บังคับกติกาเดียวกันทั้ง UI และ REST (รวมการเรียก PostgREST โดยตรง)
- กัน cross-user IDOR: user A ต้องไม่สามารถอ่าน แก้ หรือสร้างออเดอร์ในนาม user B ได้
- ฝั่ง client แก้ไขราคาหรือยอดรวมไม่ได้ ราคาและยอดรวมคำนวณในฐานข้อมูลจากราคาเมนูจริง
- รายการที่ `is_available = false` สั่งผ่าน RPC/REST โดยตรงไม่ได้
- Insert ทำผ่าน RPC เท่านั้น ไม่เปิด `INSERT`/`UPDATE`/`DELETE` ตรงให้ `anon` หรือ `authenticated` บน `orders` และ `order_items` (ยกเว้นสิทธิ์ที่จำเป็นต่อการทำงานของ RPC ฝั่งเซิร์ฟเวอร์)
- role `anon` ไม่มีสิทธิ์เข้าถึง `orders` และ `order_items`
- ห้ามมี secret หรือ `service_role` key ฝั่ง client
- การทดสอบความปลอดภัยของ UC03 รวมอยู่ในชุดที่ 204 ตรวจตาม UC02 โดยเฉพาะ V4 Access Control และ cross-user IDOR รวมถึงการปลอมราคาและการเรียก RPC/REST โดยไม่ล็อกอิน
- การทดสอบแบบ active บน mockup ทำได้ แต่ห้ามใช้คำสั่ง `DROP`, `TRUNCATE`, `ALTER` ห้ามเปลี่ยนข้อมูลเมนู baseline และหลังมีการเขียนข้อมูลต้องคืน baseline
